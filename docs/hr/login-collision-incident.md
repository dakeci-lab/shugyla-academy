# Инцидент — приём кандидата со занятым логином молча склеивал два разных сотрудника

**Направление:** аудит + фикс (Edge Function) + защита (сервер + форма).
**Дата:** 2026-08-28.
**Кейс:** при оформлении кандидата «Жанерке Қалдыбек» (заявка 24.08.2026, вакансия «Продавец-мерчендайзер») в форму найма был указан логин `janerke`, который уже принадлежал другому активному сотруднику. Система не показала ошибку «логин занят» и отрапортовала об успешном создании сотрудника.

---

## Вердикт

`academy_users.login` **уникален на уровне БД** (`unique` в `supabase/schema.sql:10`) — прямой одновременной записи двух строк с одинаковым логином произойти не могло. Проблема была в Edge Function `admin-create-employee`: при коллизии логина с уже полностью заведённым (`auth_user_id is not null`) сотрудником функция возвращала **200 OK с данными чужого, старого сотрудника** вместо `409 conflict`, помечая ответ `idempotent: true`. Расчёт был на повтор одного и того же запроса (сеть моргнула, двойной клик), но проверка шла **только по логину**, без привязки к конкретному кандидату/запросу — поэтому она же срабатывала и когда логин случайно совпал у **другого** кандидата.

Фронтенд (`EmployeeEditModal.jsx`) получал этот «успех» и вёл себя так, будто сотрудник создан заново:
1. привязывал **нового** кандидата к `id` **старого** сотрудника (`linkCandidateToEmployee`);
2. заливал фото нового кандидата в `avatar_url` старого сотрудника (`transferCandidatePhotoToEmployee` → `updateEmployee`);
3. все остальные введённые в форму значения (роль, должность, дата приёма) никуда не сохранялись — сервер их просто не принимал, раз не создавал новую строку.

Никакой ошибки при этом не показывалось — отсюда ощущение «программа просто перезаписала».

## Доказательства

### Код

| Что | Где |
|---|---|
| Ложная «идемпотентность» по логину | `supabase/functions/admin-create-employee/index.ts:278` (до фикса) |
| Легитимная идемпотентность по кандидату (не трогалась) | `supabase/functions/admin-create-employee/index.ts:232` |
| Привязка кандидата к чужому `id` | `src/services/recruitmentSupabaseAdapter.js:418` (`linkCandidateToEmployee`) |
| Безусловная перезапись аватара | `src/services/candidatePhotoService.js:226` (`transferCandidatePhotoToEmployee`) → `admin-update-employee` (`avatar_url` разрешён в `ALLOWED_CHANGE_KEYS`) |
| Уникальность логина в БД (не нарушалась) | `supabase/schema.sql:10` |

### Проверка в проде (read-only, через UI)

Кандидат «Жанерке Қалдыбек» — единственная заявка с этим именем (все статусы кандидатов проверены). Сотрудник с логином `janerke` — единственная запись (проверено включая уволенных). У сотрудника стояла её фотография и должность «Кассир», хотя заявка была на «Продавец-мерчендайзер» — то есть после коллизии реально сохранились только логин/аккаунт и фото; остальные поля формы найма были отброшены.

---

## Фикс

`supabase/functions/admin-create-employee/index.ts` — убрана ветка «логин занят и уже привязан к auth → вернуть как успех». Коллизия логина **всегда** `409 conflict`, кроме повторного запроса того же кандидата (`source_candidate_id`, проверка выше по коду — не менялась).

Соответствует уже существовавшему тесту `scripts/verify-employee-provisioning.mjs` → `stageDuplicateTests()` (ожидает `409` на дубль логина) — то есть фикс возвращает поведение к тому, что тест всегда и предполагал.

Прогон `npm run supabase:local:verify-employee-provisioning` в этой сессии не завершён (среда заблокировала запуск Docker-теста классификатором авто-режима) — нужно прогнать вручную для зелёной галочки.

---

## Защита от повторения

1. **Сервер** (`admin-create-employee`) — конфликт логина теперь всегда жёсткая ошибка, независимо от того, кто и как её вызвал (форма кандидата, прямое создание сотрудника, будущие вызовы).
2. **Форма** (`EmployeeEditModal.jsx`) — новая живая проверка логина при создании сотрудника: debounce 500мс → `admin-check-employee-login` (новая read-only Edge Function, право `employees.create`) → если занято, подбирает и предлагает свободный вариант с числовым суффиксом (`janerke` → `janerke1`/`janerke2`…). Проверка вспомогательная (advisory) — серверный `409` при сабмите остаётся источником истины на случай гонки.

## Восстановление данных

Второй реальный человек («Жанерке Қайнарбек», кассир) в базе не существовал вообще — ни как сотрудник, ни как кандидат: её попытка найма была полностью проглочена багом (для прямого создания сотрудника, не через кандидата, фронтенд на коллизии вообще ничего не делает с ответом сервера — ни привязки, ни фото, форма просто закрывается с сообщением «Сотрудник создан»). Восстановлено через админку:
- существующая запись `janerke` (Жанерке Қалдыбек) — должность исправлена на «Продавец-мерчендайзер» (соответствует её анкете и фото);
- заведена новая запись `janerke1` (Жанерке Қайнарбек) — кассир, отдельный логин и пароль.
