# PR 1 — модуль «Счета оплаты» (справочник, без потребителей)

## 0. Статус: реализовано, проверено в браузере (npm run dev, локальный режим)

## 1. Контекст

Аудит показал, что «способ оплаты» поставщика (`platform_suppliers.payment_type`)
исторически был enum из 4 значений (`cash`/`transfer`/`deferral`/`mixed`), где
способ и срок отсрочки были смешаны в одном поле — см.
[docs/suppliers/single-payment-terms-field.md](single-payment-terms-field.md).

Владелец хочет не просто развязать «способ» и «срок» на 2 независимых поля
(это первоначальный запрос), а сделать «способ» полноценным пользовательским
справочником — «счета оплаты» (Наличные, Kaspi, Halyk, ...), которые можно
создавать, переименовывать и деактивировать самостоятельно, под будущий
финансовый модуль.

Это PR 1 из двух: сам модуль справочника, без интеграции с поставщиками.
PR 2 (следующий, отдельный) подключит `platform_suppliers.payment_account_id`
и обязательства (`supplier_payment_obligations`) к этой таблице, уберёт старый
enum `payment_type`.

## 2. Решение

**Таблица** `payment_accounts` (миграция
`20260914120000_payment_accounts.sql`): `name`, `description`, `is_active`,
`sort_order`. Без hard-delete — только `is_active=false`, тот же паттерн, что
у `roles` (`rbac_set_role_active`). Уникальность имени — по
`lower(btrim(name))`, защищает от «Kaspi» и «kaspi » одновременно.

**RBAC**: новый модуль прав `payment_accounts.view` / `payment_accounts.manage`
— отдельное право, не завязанное на `suppliers.edit` (по решению владельца —
это общий справочник на всех поставщиков, а не часть карточки одного
поставщика). Выдан по умолчанию только роли `admin`; другим ролям можно
выдать через существующий редактор ролей.

**RLS**: `select` — `using (true)`, как у `roles`/`permissions` (любой
залогиненный пользователь может видеть список — это просто имена, а не
чувствительные данные, и понадобится PR 2 для дропдауна в карточке
поставщика). `insert`/`update` — гейтятся `payment_accounts.manage`. Прямого
DELETE нет ни в RLS, ни в адаптерах — деактивация вместо удаления.

**Данные**: `paymentAccountsLocalAdapter.js` (localStorage, сид «Наличные»/
«Перевод») + `paymentAccountsSupabaseAdapter.js` (прямые запросы к таблице,
без RPC — простой CRUD без матрицы прав, в отличие от ролей), переключаются
через `paymentAccountsService.js` (`isCloudMode()`), тот же паттерн, что
`rbacService.js`.

**UI**: новая вкладка «Счета оплаты» в Настройках
(`/platform/settings/payment-accounts`), список + модалка создания/
редактирования, по образцу `RolesListTab`/`useRoleEditor`, но без матрицы
разрешений — только название, описание, статус.

## 3. Проверка

### 3.1 Verify-скрипт

```bash
npm run verify:payment-accounts-module
```

46 проверок: чистые функции (`normalizePaymentAccount`, `sortPaymentAccounts`,
`findPaymentAccountNameConflict`), миграция (таблица/RLS/права/сид),
подключение RBAC/роута/навигации, адаптеры и сервис, UI-компоненты.

### 3.2 Реальный рендер в браузере

`npm run dev` (локальный режим, без `.env.local` → localStorage-адаптер),
вход `admin`/`admin123` (см. `src/data/users.js`). Проверено вручную:

| Шаг | Результат |
|---|---|
| Настройки → Счета оплаты | Список из 2 сидированных счетов: «Наличные», «Перевод», оба активны |
| Создание «Kaspi Gold» | Появляется в списке, статус «Активен» |
| Деактивация «Kaspi Gold» | Статус → «Неактивен», кнопка меняется на «Активировать», тост подтверждения |
| Переименование «Наличные» → «Перевод» | Отклонено с ошибкой «Счёт «Перевод» уже существует», ничего не сохранено |
| Пункт навигации | «Счета оплаты» появляется в дропдауне «Настройки» рядом с «Роли и доступы» |

Прод-миграция (реальная Supabase) не прогонялась — нет `.env.local`/Docker в
этой среде; синтаксис проверен только статически (verify-скрипт читает
исходник SQL текстово, не выполняет).

## 4. Preflight перед прод-деплоем

```bash
npm run build
npm run verify:payment-accounts-module
```

Нужно подтвердить на реальной Supabase: применить миграцию, зайти под
админом на `web.shugyla-market.kz/platform/settings/payment-accounts`,
убедиться что сид (Наличные/Перевод) появился, попробовать создать/
деактивировать счёт.

## 5. Критерии приёмки

- [ ] Вкладка «Счета оплаты» доступна из Настроек только тем, у кого есть
      `payment_accounts.view` или `payment_accounts.manage` (по умолчанию —
      только admin).
- [ ] Создание, переименование, деактивация/активация счёта работают.
- [ ] Нельзя создать два счёта с одинаковым именем (без учёта регистра/
      пробелов).
- [ ] Деактивированный счёт нельзя удалить физически — он остаётся в списке
      со статусом «Неактивен».
- [ ] Ничего в карточке поставщика или в «К оплате» пока не изменилось —
      это отдельный модуль без потребителей (PR 2).
