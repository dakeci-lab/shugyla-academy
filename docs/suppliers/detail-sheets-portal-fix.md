# Фикс — карточка деталей открывается посреди страницы вместо экрана

## 0. Статус: реализовано, подтверждено измерением и реальным рендером в браузере

## 0.1 Регресс после первой версии фикса (найден владельцем в проде)

Первая версия этого PR (`e20718a`) сама сломала «Взаиморасчёты»: клик на
любую операцию внутри карточки поставщика стал выкидывать общий экран
`PlatformErrorBoundary` («Не удалось открыть платформу», код `pwa-...`)
вместо карточки. Владелец поймал это в реальном использовании и прислал
скриншот с кодом ошибки — в этой среде нет логина, чтобы поймать такое
самому кликом, поэтому нашёл через анализ кода и подтвердил реальным
React-рендером компонента в браузере (см. §2.1).

**Причина регресса:** в `OperationDetailSheet.jsx` уже был локальный
`useState` с именем `document` (это загруженный объект UMAG-документа —
бизнес-сущность, а не DOM), который перекрывает глобальный `document` во
всей области видимости компонента:

```js
const [document, setDocument] = useState(null)
```

Мой `createPortal(..., document.body)` внутри этого файла обращался не к
`window.document`, а к этому состоянию — которое при первом рендере `null`.
`null.body` → `TypeError: Cannot read properties of null (reading 'body')`
→ React ловит это `PlatformErrorBoundary`'ем (единственным глобальным error
boundary, оборачивающим весь контент платформы) и подменяет **весь раздел**
на общий экран с «Повторить/Обновить/Выйти из аккаунта» — без всякой связи
с реальной причиной.

**Фикс:** заменил `document.body` на `window.document.body` в этом файле
(единственный файл из двух, где есть такая тень — в `SupplierPaymentsPanel.jsx`
`document` не переопределён, там `document.body` в `GroupDetail` всегда был
корректен). Добавлена регресс-проверка (Case 4b в verify-скрипте) и реальный
рендер-тест в браузере, не только regex по исходнику — regex не может
поймать переменную-тень, только выполнение кода.

## 2.1 Реальный рендер-тест регресса (не только regex)

Regex по исходнику не отличает `document.body` от `window.document.body` в
контексте, где обе строки — валидный JS: он не видит, что имя `document`
переопределено выше по файлу. Единственный надёжный способ поймать такую
переменную-тень — реально выполнить компонент. Собрал временный Vite-entry
(`__scratch_operation_sheet_test.jsx` + `.html`, не коммитились), смонтировал
`OperationDetailSheet` напрямую с фикстурными данными (`kind: 'payment'` —
не требует сети) через `createRoot` в реальном браузере на деве:

```json
{"mounted": true, "renderError": null, "hasBackdrop": true, "backdropParent": "BODY", "title": "Фуд Мастер"}
```

`backdropParent: "BODY"` подтверждает, что портал реально попал в
`document.body`, а не упал раньше. Скриншот — карточка «Оплата поставщику»
отрендерилась корректно, без ошибки.

## 1. Проблема (репорт владельца)

В «К оплате» клик по строке (например, «СПК товары», самая верхняя строка)
не показывал карточку деталей — она открывалась «где-то посреди страницы»,
и чтобы её увидеть, нужно было прокрутить вниз, независимо от того, где был
клик и в какой точке экрана.

## 2. Причина (подтверждена измерением, не только чтением кода)

`GroupDetail` (карточка деталей строки, `SupplierPaymentsPanel.jsx:376`) —
`position: fixed`, но рендерится инлайн, глубоко внутри дерева страницы
(`SupplierFinancePanel` → `SupplierPaymentsPanel` → `GroupDetail`), а не через
React-портал.

Весь контент платформенных страниц обёрнут в `PullToRefresh`
(`src/components/platform/PullToRefresh.jsx:157`), у обёртки которого
(`.pull-to-refresh__body`) в CSS стоит `will-change: transform`
**постоянно** — не только во время реального перетягивания
(`PullToRefresh.css:15`).

По спецификации CSS `will-change: transform` создаёт для `position: fixed`
потомков новый containing block — так же, как настоящий `transform`.
Поэтому «fixed» карточка на самом деле позиционируется не относительно окна
браузера, а относительно этой обёртки, которая по высоте равна **всей
странице**. `align-items: center` центрирует её не в видимой области, а в
середине всей прокручиваемой страницы.

**Подтверждено измерением**, не только рассуждением: собрал минимальную
HTML-репродукцию той же структуры (`will-change: transform` на обёртке +
вложенный `position: fixed`-потомок против такого же элемента-портала на
уровне `body`) и снял `getBoundingClientRect()` при `scrollY: 0`,
`innerHeight: 841`:

| | top |
|---|---|
| инлайн (внутри `will-change`-обёртки) | **1472.5px** — далеко за пределами экрана |
| портал (в `document.body`) | **393px** — ровно по центру экрана |

Это тот же баг, что и в предыдущем PR про «Расчёты»: `AdminModal.jsx` уже
решает его правильно через `createPortal(..., document.body)` — модалки на
его основе (например, «Создать акт сверки») не ломаются. Такая же проблема
была и в `OperationDetailSheet.jsx` (Взаиморасчёты → клик на поставщика →
клик на операцию) — найдено в ходе этого же разбора, ещё не зарепорчено
владельцем, но сломалось бы точно так же при первом клике.

## 3. Решение

`SupplierPaymentsPanel.jsx` (`GroupDetail`) и `OperationDetailSheet.jsx` —
оба теперь `return createPortal(<...>, document.body)`, по образцу
`AdminModal.jsx`. Только точка рендера; ни разметка, ни `role="dialog"`/
`aria-modal`/`aria-label`, ни логика клика не менялись.

Не тронуто (сознательно, не входило в репорт): блокировка скролла страницы
и закрытие по Escape, которые уже есть у `AdminModal`, здесь так и остаются
отсутствующими — это отдельное UX-улучшение, не эта позиционная ошибка.
