# Фикс — N+1 по поставщикам в umag-sync (синхронизация «Расчёты» слишком долгая)

## 0. Статус: реализовано; `deno check`/`deno lint` чистые, живой прогон синка не делал (нет Docker/Supabase в этой среде)

## 1. Проблема (репорт владельца)

Клик ↻ в «Расчёты» (любая из трёх кнопок — «К оплате», «Взаиморасчёты»,
общая) выполняется подозрительно долго.

## 2. Замер (сначала измерение, как и требует процесс проекта)

Реальная история из `umag_sync_runs` (владелец прислал по моему запросу):

| entity | records_received | returns_received | длительность |
|---|---|---|---|
| `all` (кнопка «Расчёты») | 740 | 23 | **124–138 сек** |
| `sales_facts` (несвязанная синхронизация продаж, для сравнения) | 5900–7235 | — | **28–54 сек** |

На запись: `all` — ≈175 мс/запись, `sales_facts` — ≈6 мс/запись. Разница
**в 25–30 раз** на сопоставимом или даже меньшем объёме данных — то есть
дело не в объёме («лишнее отсканировал» не подтвердилось буквально), а в
том, *как* эти записи обрабатываются.

## 3. Причина

`reconcileCanonicalSuppliers()` (`supabase/functions/umag-sync/index.ts:719`)
выполняется **при каждом клике** (все три кнопки синхронизации вызывают
`syncSuppliers: true`), и для каждого поставщика из UMAG делала **отдельный
awaited запрос** — либо `UPDATE`, либо `INSERT` — строго последовательно, в
цикле `for (const umag of umagRows...)`. При ~200+ поставщиках в каталоге
это сотни последовательных сетевых round-trip'ов на каждый клик, хотя
каталог поставщиков в UMAG почти не меняется день в день.

Второй такой же N+1 (починка «осиротевших» связей платежей в перестройке
журнала операций) и отсутствие инкрементальной синхронизации (полный
перезапрос из UMAG каждый раз, без курсора «с последнего раза») — тоже
найдены, но не входят в этот PR (см. §6 «Отложено»).

## 4. Решение

Переписал `reconcileCanonicalSuppliers()` в три фазы:

1. **Цикл принятия решений** (без единого обращения к БД) — для каждого
   UMAG-поставщика определяется: обновить существующего (по
   `umag_supplier_id` или уникальному БИН) или создать нового. Решения
   складываются в `updateDecisions`/`insertDecisions`. Безопасно, потому
   что решение по каждой строке зависит только от карт, построенных **до**
   цикла (`byUmagId`, `unlinkedByBin`, `umagBinCounts`) — ни одна запись не
   зависит от результата записи другой в рамках одного прогона (уникальный
   БИН гарантированно встречается только у одного UMAG-поставщика за
   прогон, так что коллизий между итерациями быть не может).
2. **Пакетное обновление** — один `upsert(..., {onConflict:'id'})` на
   чанк из 100 строк вместо одного `UPDATE` на поставщика. Пишутся
   по-прежнему только UMAG-поля (`umagOwned`) — тот же принцип, что и
   раньше («Shugyla operational fields are never written here»).
3. **Пакетная вставка** — один `INSERT` на чанк из 100, с
   `.select('id, umag_supplier_id')`: `umag_supplier_id` в каждой строке
   позволяет сопоставить вернувшиеся `id` с исходным решением **без
   зависимости от порядка** ответа Postgres.

Итоговый контракт не изменился: `mappingErrors > 0` по-прежнему проваливает
весь этап синка (`CANONICAL_SUPPLIER_RECONCILE_FAILED`) — просто теперь
считается по чанкам, а не по строкам, что не меняет исход (провал есть
провал в обоих случаях), только уменьшает гранулярность отчёта об ошибке.

## 5. Verify

```bash
npm run verify:umag-sync-canonical-batch
deno check supabase/functions/umag-sync/index.ts
deno lint supabase/functions/umag-sync/index.ts
```

`deno check`/`deno lint` дают те же 7/3 ошибки, что и на чистом `main`
(в других файлах, `_shared/umagAuth.ts`/`_shared/employeeAuthorization.ts`,
не мои) — ни одной новой.

Это Deno Edge Function — импортировать в Node-скрипт напрямую нельзя
(`Deno.serve` на верхнем уровне модуля, функция не экспортирована) — тот же
ограничение, что уже описано в `verify-supplier-finance-sync-scope.mjs`.
7 структурных проверок пиннят точную форму фикса: цикл решений больше не
делает `await` на запись, обновления/вставки идут пачками, сопоставление
вставленных строк — по `umag_supplier_id`, а не по порядку ответа, контракт
провала синка не изменился, логика сопоставления (по внешнему id, потом по
уникальному БИН) не тронута.

Живой прогон синхронизации не делал — нет Docker/Supabase в этой среде.
**Нужно подтвердить кликом ↻ в проде** и сверить новую длительность с
`umag_sync_runs`.

## 6. Отложено (не в этом PR)

- Второй N+1 — починка «осиротевших» связей платежей в
  `rebuildLedgerEventsForPeriod()` (`_shared/umagDocumentPayments.ts`).
- Настоящая инкрементальная синхронизация (курсор по `editTime`/
  `last_synced_at` вместо полного перезапроса каждый раз) — самый глубокий
  и самый рискованный рычаг, отдельная задача.

## 7. Критерии приёмки

- [ ] Синхронизация «Расчёты» (`entity: all`) стала заметно быстрее в
      `umag_sync_runs` по сравнению с историческими 124–138 сек при
      сопоставимом `records_received`.
- [ ] Поставщики продолжают корректно создаваться/обновляться/
      деактивироваться при синхронизации (сверить количество
      `created`/`updated` в логах Edge Function не изменилось по смыслу).
- [ ] Обнаружение потенциальных дублей по точному совпадению имени
      по-прежнему работает для новых поставщиков.
