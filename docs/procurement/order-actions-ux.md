## 1. Проблема

Закупщик создал заказ и не может ничего в нём поправить. Кнопка «Отменить» ставит
статус `cancelled`, после чего заказ исчезает из интерфейса — выглядит как удаление,
хотя данные целы.

## 2. Что происходит на самом деле (по коду)

| Факт | Где |
|------|-----|
| Заказ из планирования создаётся сразу со статусом `awaiting_receiving`, `transferred_to_receiving = true` | `supabase/migrations/20260810160315_procurement_partial_supplier_generation.sql:363` |
| В той же транзакции создаётся документ приёмки | там же, `insert into public.receiving_documents` |
| Статусы `formed` и `sent` в облачном режиме не выставляются никогда | `PURCHASE_STATUS` в `src/utils/purchaseData.js:7`; в `purchaseSupabaseAdapter.js` не используются |
| Правка позиций разрешена только в черновике | `src/pages/platform/procurement/PurchaseDetailPage.jsx:71` — `canEditItems = canEdit && status === DRAFT` |
| Отменённые заказы жёстко вырезаны из списка | `src/pages/platform/procurement/ProcurementPage.jsx:158` и `:164` |
| После отмены страница уходит в список | `PurchaseDetailPage.jsx:252` — `navigate('/platform/procurement')` |
| Отмена заказа **не** отменяет документ приёмки | `purchaseSupabaseAdapter.js:530` — `cancelPurchaseOrderCloud` меняет только `purchase_orders.status` |
| `purchase_orders` и `receiving_documents` доступны `authenticated` на update | `20260717210000_secure_procurement_rls.sql:51,148` |

Ключевое следствие: **стадии «черновик» у заказов из планирования не существует.**
Заказ рождается уже переданным в приёмку. Поэтому нужен явный возврат в черновик.

Второй важный дефект, найденный попутно: отмена заказа оставляет документ приёмки
в статусе `awaiting_receiving` — склад продолжает ждать поставку по отменённому заказу.

## 3. Принятые решения

| Вопрос | Решение |
|--------|---------|
| Граница редактирования | Возврат в черновик разрешён, **пока склад не начал приёмку**. Отдельным PR позже — настоящая кнопка «Отправить поставщику» (см. §7) |
| Отменённые заказы | Скрыты из рабочего списка, доступны через фильтр «Отменённые» |
| Экспорт | **Без изменений** — две иконки, Excel и PDF, каждая в один клик. Объединение в одну кнопку с выбором отклонено: превращает один клик в два |
| Удаление черновика | Мягкое: статус `cancelled`, запись остаётся в БД. Физического удаления нет |

## 4. Условие «приёмка не начата»

Возврат в черновик и отмена заказа разрешены только когда связанный документ приёмки
не тронут складом:

```
receiving_documents.status = 'awaiting_receiving'
AND receiving_documents.total_received_qty = 0
```

Если приёмка началась (`in_progress`, `partially_received`, `received`, либо
`total_received_qty > 0`) — кнопка «Редактировать» **не отображается**, а не отключается.
Отключённая кнопка без объяснения раздражает; вместо неё показать текстовую подсказку
в блоке действий: «Склад начал приёмку — заказ изменить нельзя».

## 5. Кнопки на карточке заказа

Панель действий — `PurchaseDetailPage.jsx:271–302`.

| Кнопка | Когда видна | Действие |
|--------|-------------|----------|
| Excel (иконка) | всегда, если есть позиции | без изменений |
| PDF (иконка) | всегда, если есть позиции | без изменений |
| **Редактировать** (карандаш) | `procurement.edit` + статус `awaiting_receiving` + приёмка не начата | подтверждение → заказ в `draft` |
| Передать в приёмку | `procurement.edit` + `!transferredToReceiving` (уже есть) | без изменений |
| **Отменить заказ** | `procurement.edit` + статус не `cancelled`/`received` + приёмка не начата | подтверждение → `cancelled`, остаётся на странице |
| **Удалить черновик** (корзина) | `procurement.edit` + статус `draft` | подтверждение → `cancelled` |

Замечание для исполнителя: «Отменить заказ» и «Удалить черновик» технически делают одно
и то же — мягкое скрытие. Разные подписи оставлены осознанно: у закупщика это разные
мысли («заказ не нужен» vs «я его ещё не отправлял»). Никогда не показывать обе
одновременно — они взаимоисключаются по статусу.

### 5.1 Действие «Редактировать»

Новая функция в сервисном слое, например `returnPurchaseOrderToDraft(orderId, user)`
в `src/services/purchaseDataService.js` (+ cloud/local реализации по существующему
паттерну адаптеров). Последовательность:

1. Перечитать заказ и связанный документ приёмки, повторно проверить условие §4
   **на сервере/в сервисе, а не только по состоянию UI** — между рендером и кликом
   склад мог начать приёмку
2. `receiving_documents.status = 'cancelled'` для связанного документа
3. `purchase_orders`: `status = 'draft'`, `transferred_to_receiving = false`,
   `receiving_document_id = null`
4. Обновить кэш через существующий `afterPurchaseMutation()`
5. Остаться на странице заказа, показать сообщение «Заказ возвращён в черновик,
   ожидаемая приёмка снята»

После этого работают уже существующие механизмы: `canEditItems` становится `true`,
позиции редактируемы, появляется кнопка «Передать в приёмку», которая создаст
**новый** документ приёмки с новым номером. Старый остаётся в истории со статусом
`cancelled` — это и есть аудиторский след.

Проверить, что `transferFromPurchase` (`src/services/receivingDataService.js`)
корректно работает для заказа с `workflowMode = 'analytics'`. Если нет — это входит в объём PR.

### 5.2 Действие «Отменить заказ»

Исправить `cancelPurchaseOrderCloud` (`purchaseSupabaseAdapter.js:530`): вместе со
статусом заказа переводить связанный документ приёмки в `cancelled`. Иначе склад
ждёт поставку по отменённому заказу — существующий дефект.

Убрать `navigate('/platform/procurement')` из `handleCancel`
(`PurchaseDetailPage.jsx:252`). Вместо этого: `refresh()`, плашка статуса «Отменён»,
сообщение. Пользователь должен своими глазами увидеть, что заказ на месте.

## 6. Список закупа: фильтр «Отменённые»

`ProcurementPage.jsx:157–172`. Убрать жёсткие `.filter(o => o.status !== CANCELLED)`
и завести переключатель состояния списка. По умолчанию — рабочий список без отменённых
(поведение как сейчас). Стиль элемента — как у существующих фильтров страницы,
новых зависимостей не вводить.

В списке отменённых у карточки серая плашка «Отменён» (`PURCHASE_STATUS_BADGE.cancelled`
уже `'idle'` — готово) и дата. Действий над отменённым заказом нет, только просмотр.

## 7. Сознательно отложено (следующий PR)

Настоящее событие отправки: генерация создаёт заказ в `draft` **без** документа приёмки,
появляется кнопка «Отправить поставщику», которая замораживает цифры и создаёт приёмку.
Это правка функции генерации в БД + перенос создания документа приёмки — денежный путь,
отдельный PR с миграцией, preflight и rollback. Не смешивать с настоящим PR.

## 8. Verify-скрипт

`scripts/verify-procurement-order-actions.mjs` → `verify:procurement-order-actions`.
Проверяет:

1. `returnPurchaseOrderToDraft` отказывает, если документ приёмки не в `awaiting_receiving`
2. отказывает, если `total_received_qty > 0`
3. при успехе: заказ `draft`, `transferred_to_receiving = false`,
   `receiving_document_id = null`, старый документ приёмки `cancelled`
4. отмена заказа переводит связанный документ приёмки в `cancelled`
5. отменённый заказ и его позиции **остались** в БД (мягкое скрытие, не удаление)
6. `PurchaseDetailPage` не содержит `navigate` в обработчике отмены
7. `ProcurementPage` не содержит безусловного отсева `CANCELLED`

## 9. Критерии приёмки

- [ ] Закупщик открывает заказ, нажимает «Редактировать» → заказ в черновике, количества редактируемы

- [ ] Отменённые заказы видны через фильтр, из рабочего списка убраны
- [ ] Кнопки экспорта не изменились — по-прежнему две иконки
- [ ] Ни одной новой миграции, ни одной новой зависимости в `package.json`
- [ ] `verify:procurement-order-actions` зелёный локально
