# Жизненный цикл заказа поставщику: аудит и план (2026-10-28)

Статус: **только аудит и проект, код не менялся.** Ждёт решения владельца (см. «Вопросы» внизу).

## 1. Что есть сейчас

### Статусы заказа (`purchase_orders.status`)
| Статус | Подпись | Живёт в БД | Кто ставит |
|---|---|---|---|
| `awaiting_receiving` | Ожидает приёмки («сохранённый») | 771 | создание заказа из «Закупа» (RPC `generate_procurement_orders_from_snapshot`), повторная передача в приёмку |
| `received` | Принят | 168 | приёмка склада |
| `cancelled` | Отменён | 20 | RPC `procurement_cancel_order` |
| `draft` | Черновик | 0 сейчас | RPC `procurement_return_order_to_draft` (кнопка-карандаш) |
| `formed`, `sent`, `partially_received` | — | 0 | **нигде не ставятся** (мёртвые значения) |

Статусы документа приёмки (`receiving_documents.status`): `awaiting_receiving` → `in_progress` («склад начал», подпись «Черновик») → `received`; `cancelled`.
Заказ и документ приёмки связаны (`receiving_document_id`) и меняются вместе внутри RPC.

### Два вида заказов
- `analytics` — создаются из планирования «Закуп» (714 из 959, **все свежие**, в т.ч. заказ со скриншота). Несут привязку к снимку плана (`source_snapshot_id`, `attempt_key`).
- `simple` — созданы вручную (87 ожидают, 158 приняты).

### Что можно делать сейчас
| Статус | Отменить | Вернуть в черновик (карандаш) | Править позиции |
|---|---|---|---|
| Ожидает приёмки, склад не трогал | да | **только `simple`** | нет |
| Ожидает приёмки, склад начал (`in_progress`, 11 шт.) | нет (сообщение «Склад начал приёмку») | нет | нет |
| Черновик | «удалить» = отмена | — | да, но только `simple` |
| Принят | нет | нет | нет |
| Отменён | — | **нет** | нет |

### Почему у заказа со скриншота только «Отменить»
1. Фронт: `canReturnPurchaseToDraft` требует `workflow_mode = simple`.
2. БД: RLS на `purchase_orders` / `purchase_order_items` разрешает UPDATE/INSERT/DELETE **только для `simple`**; триггер `purchase_orders_guard_analytics_identity` запрещает менять привязку к снимку.
3. RPC `procurement_return_order_to_draft` режим не проверяет — запрет только в интерфейсе.

### Что делает отмена заказа из планирования (важно)
`procurement_cancel_order` возвращает количества в снимок плана (`final_order_qty := ordered_qty`, `generated_purchase_order_id := null`). Сейчас это единственный путь «поправить»: отменить → в «Закупе» количества вернулись → собрать заказ заново.

### Найденные нестыковки
- 2 отменённых заказа (14.08) имеют документ приёмки в `awaiting_receiving` — отмена была до RPC; склад может их видеть. Нужна одноразовая чистка (перевести документы в `cancelled`).
- Повторная передача в приёмку (`transferFromPurchaseCloud`) делается **с клиента несколькими записями**, не одной транзакцией (в отличие от отмены/возврата) — для заказа из планирования это ещё и упирается в RLS.
- «В пути» в плане считает заказы «не отменён / не принят» с датой ≥ сегодня — черновик тоже учитывается как «в пути».
- Нет журнала: кто и когда вернул/отменил/изменил заказ.

## 2. Целевая схема (предложение)

```
                  ┌────────────── Редактировать ──────────────┐
                  ▼                                           │
 ┌──────────┐  Сохранить  ┌────────────────────┐  склад начал  ┌──────────────┐  завершил  ┌────────┐
 │ ЧЕРНОВИК │────────────▶│ СОХРАНЁН           │──────────────▶│ ПРИЁМКА      │───────────▶│ ПРИНЯТ │
 │ (правим) │             │ (awaiting_receiving│   (склад)     │ ИДЁТ         │            │ (итог) │
 └──────────┘             │ склад ждёт)        │               │ (in_progress)│            └────────┘
   │   ▲                  └────────────────────┘               └──────────────┘
   │   │ Восстановить            │ Отменить                      правки и отмена закрыты:
   │   │                         ▼                               только склад
   │   └───────────────── ┌──────────┐
   └── Удалить ──────────▶│ ОТМЕНЁН  │
                          └──────────┘
```

| Из статуса | Что доступно закупщику | Куда ведёт |
|---|---|---|
| Сохранён (склад не трогал) | Редактировать · Отменить · Скачать | Черновик · Отменён |
| Черновик | менять количества, добавлять/удалять позиции, дата, комментарий · **Сохранить** · Удалить | Сохранён · Отменён |
| Отменён | **Восстановить** (в черновик) · Скачать | Черновик |
| Приёмка идёт | только просмотр и скачивание, подсказка «Склад начал приёмку» | — |
| Принят | только просмотр и скачивание | — |

Правила:
- «Сохранить» нельзя с пустым заказом (все позиции удалены) — предложить «Удалить заказ».
- Редактирование снимает отметку «Сверено» (уже так сделано) и документ приёмки; при «Сохранить» создаётся новый документ приёмки с актуальными количествами.
- Подписи в интерфейсе: «Ожидает приёмки» можно переименовать в «Сохранён» (по вашей терминологии) — решение ниже.

## 3. Что нужно сделать (этапы, один PR = одно направление)

1. **БД, атомарные RPC** (с проверкой прав `procurement` и блокировкой строк, как у отмены):
   - `procurement_save_order_edit(order_id, items jsonb, expected_date, comment)` — только `draft`; пересчитывает суммы/кол-во позиций; для обоих видов заказов, привязка к снимку не трогается;
   - `procurement_submit_order(order_id)` — `draft` → `awaiting_receiving` + документ приёмки и позиции одной транзакцией (замена клиентской передачи);
   - `procurement_restore_order(order_id)` — `cancelled` → `draft` (+ проверка дублей, см. риск 1);
   - снять запрет по `simple` в `procurement_return_order_to_draft` не нужно (его и нет) — снимается только фронтовая проверка.
   RLS/триггеры для прямых записей не расширяем: всё через RPC.
2. **Фронт**: убрать проверку `simple`; в карточке — кнопки по таблице выше; в черновике редактирование позиций через RPC; «Восстановить» у отменённых.
3. **Журнал** `purchase_order_events` (заказ, событие, кто, когда, было→стало) + блок «История» в карточке. Желательно, не блокирует.
4. **Чистка данных**: 2 отменённых заказа с живыми документами приёмки.
5. `verify:*` на матрицу переходов, документ этапа с preflight/postcheck/откатом.

## 4. Риски
1. **Двойной заказ при восстановлении.** После отмены количества вернулись в план «Закупа»; если закупщик собрал новый заказ тому же поставщику, а потом восстановил старый — получится два. Защита: восстановление блокируется, если у поставщика есть активный заказ на ту же дату доставки; иначе при восстановлении снимок снова «гасится».
2. **Склад в гонке с правкой.** Закупщик сохраняет, пока склад уже нажал «начать приёмку». Закрывается повторной проверкой под блокировкой строки внутри RPC (как у отмены).
3. **План «в пути».** Черновик считается «в пути» (консервативно). Предлагаю оставить, чтобы не заказать повторно на время правки.
4. **Старые заказы.** Правка 714 «аналитических» заказов не меняет их привязку к плану; задним числом пересчёт плана не делается.
