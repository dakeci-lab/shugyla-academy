# Механика столбцов таблиц в UMAG (web.umag.kz) — техническая опись для переноса на платформу Shugyla

> Источник: живое исследование раздела «Товары → Список товаров» в web.umag.kz через DOM-инспекцию,
> перехват fetch/XHR и чтение сетевых запросов. Все выводы ниже подтверждены техническими данными
> (классы CSS, тело запросов), а не только визуальным наблюдением. Помечено «предположение» там,
> где вывод сделан по косвенным признакам, а не проверен напрямую.

## 1. Что это и зачем этот документ

UMAG — это ERP для розницы (тот же класс систем, что и наша платформа Shugyla), и раздел «Список
товаров» — это большая таблица с ~15+ столбцами, которую пользователь может настраивать под себя:

1. **Менять ширину столбца** — тянуть правую границу заголовка.
2. **Менять порядок столбцов** — перетаскивать заголовок целиком.
3. **Скрывать/показывать столбцы** — через панель «Видимость столбцов» (иконка-шестерёнка).

Все три настройки **сохраняются на сервере** и восстанавливаются при следующем заходе — то есть
это не просто клиентский CSS-трюк, а полноценная фича с персистентностью per-пользователь/per-магазин.

Документ описывает, как это устроено технически, чтобы реализовать аналог в наших таблицах
(закуп, приёмка, персонал и т.д.) на стеке Shugyla — React 19 без UI-библиотек, Supabase как бэкенд.

## 2. Технология-первоисточник

Таблица в UMAG — это **PrimeNG `p-table`** (Angular-библиотека компонентов). Определено по классам
на живом DOM:

```
<table class="p-datatable-resizable-table p-datatable-table ...">
```

Это важно: UMAG не изобретал resize/reorder/visibility с нуля — использовал готовые фичи PrimeNG
DataTable (`pResizableColumns`, `pReorderableColumns`, встроенный column-toggle паттерн). У нас в
проекте PrimeNG нет и вводить его не стоит (CLAUDE.md: «зависимости намеренно минимальны», «нет
UI-библиотек, не вводить новые зависимости без обсуждения») — но **логику** оттуда переносим на
чистый React + CSS.

## 3. Изменение ширины столбца (resize)

### Что видно пользователю
На правом краю каждого заголовка (`<th>`), кроме первого (чекбокс выбора строки) и последнего
(колонка с иконкой печати), есть невидимая узкая полоска ~4–6px. При наведении курсор меняется на
`col-resize`. Зажимаешь и тянешь — ширина столбца меняется в реальном времени, без лагов.

### DOM-структура
```
<th class="... p-datatable-resizable-column p-datatable-reorderable-column" style="width: 200px">
  <div class="header-div">Название столбца + иконка сортировки</div>
  <span class="p-datatable-column-resizer"></span>   <!-- сама «ручка» resize -->
</th>
```

Ключевая деталь: `<span class="p-datatable-column-resizer">` — это абсолютно позиционированный
элемент внутри `<th>`, прижатый к правому краю, шириной в несколько пикселей, с `cursor: col-resize`.
Он перехватывает `mousedown`, дальше на `document` вешаются `mousemove`/`mouseup`, ширина `<th>`
обновляется через инлайн `style.width` при каждом движении мыши.

### Как ширина применяется ко всей колонке (важная техническая деталь)
В таблице **нет `<colgroup>`** и ширина явно не проставлена на каждой `<td>` — только на `<th>`.
Работает это благодаря CSS:

```css
table { table-layout: fixed; }
```

При `table-layout: fixed` браузер сам выравнивает ширины ячеек `<tbody>` по ширине ячеек `<thead>`
в той же колонке (по индексу, не по содержимому). Это единственный CSS-трюк, который нужен —
**не нужно** синхронизировать ширину каждой строки вручную. Это прямо переносимая рекомендация
для нашего стека: если будем делать resize на чистом `<table>`, `table-layout: fixed` обязателен.

### Режим resize: «expand», не «fit»
Проверено эмпирически: при расширении столбца «Наценка %» на 65px соседние столбцы **не сжались** —
их ширина в сохранённом состоянии осталась прежней. То есть используется режим, при котором
**вся таблица становится шире**, а не «отбирается» ширина у соседа. У таблицы уже есть
горизонтальный скролл-контейнер (с самого начала, до всех наших изменений) — значит это ожидаемое
поведение, а не побочный эффект.

### Минимальная ширина
Наблюдался пол ~50px (столбец не сжимался ниже этого значения при перетаскивании до упора).
Совпадает с фиксированной шириной служебных колонок (чекбокс выбора, иконка печати) — похоже на
общий `min-width` по умолчанию (предположение, не проверено на 100%).

### Сохранение
На **окончание** перетаскивания (не на каждый `mousemove`) уходит один сетевой запрос — см. раздел 6.

## 4. Изменение порядка столбцов (reorder)

### Что видно пользователю
Перетаскиваешь **сам заголовок** (не resize-полоску, а основную область `<th>` с текстом) влево
или вправо, переносишь через середину соседнего заголовка — столбцы меняются местами. Отпускаешь —
порядок применяется мгновенно.

### Технически
Класс `p-datatable-reorderable-column` есть на каждом `<th>` рядом с `p-datatable-resizable-column` —
то есть resize и reorder на одном и том же заголовке работают одновременно, но через разные зоны
захвата: узкая полоска справа = resize, остальная область заголовка = reorder (PrimeNG сам разводит
эти два жеста по зоне клика).

### Что происходит при drop
При отпускании **пересчитываются номера позиций всех столбцов** (0..N-1 по порядку слева направо),
и на сервер уходит **весь массив столбцов целиком** — не дельта «столбец X переместился с позиции 3
на позицию 7», а полный снэпшот состояния таблицы. Подтверждено сравнением тела запроса до/после
drag: у всех 16 столбцов пересчитан `columnOrdinalNumber`.

Вывод для переноса: **не пытаться слать diff** — проще на каждое изменение (resize/reorder/toggle)
сериализовать текущий полный список колонок и отправлять целиком. Это резко упрощает и бэкенд
(один upsert), и фронтенд (один `saveTableSettings(columns)` вызывается из трёх разных обработчиков).

## 5. Видимость столбцов (column visibility toggle)

### Что видно пользователю
Иконка-шестерёнка в правом верхнем углу таблицы (последняя «ячейка» шапки). Клик открывает
всплывающую панель:

```
Видимость столбцов
Настройте таблицу под себя и ваш выбор сохранится

☑ Код НКТ (NTIN)
☑ Артикул
☑ Доп. код
☑ Закуп. цена
☑ Ед. изм
☑ Прод. цена
☑ Наценка
☑ Маржа
☑ Номер на весах
☑ Дата изм.
☑ Поставщик
```

Плоский список чекбоксов, **без drag-хендлов** (то есть порядок здесь не меняется — только
показать/скрыть). Клик по чекбоксу мгновенно скрывает/показывает колонку в таблице **без кнопки
«Применить»/«Сохранить»** — автосохранение на каждый клик.

### Важный нюанс: не все столбцы можно скрыть
В списке чекбоксов **нет** первых двух и последнего столбца таблицы: чекбокс выбора строки,
«Название товара», «Штрихкод» и иконка печати. Они всегда видимы и не участвуют в тоггле —
то есть в модели данных есть понятие «системная/обязательная колонка», которую UI toggler
сознательно не показывает пользователю.

### Нет кнопки сброса
В панели нет «Сбросить по умолчанию». Единственный способ вернуть исходный вид — вручную заново
проставить чекбоксы/перетащить столбцы обратно.

### Скрытые в реестре, но не показанные в UI столбцы
В сохранённом массиве столбцов (см. ниже) оказалось **больше** колонок, чем чекбоксов в панели:
поле `ikpu` (вероятно, аналог ИКПУ — код продукции для узбекского рынка, у UMAG есть версия и для
Узбекистана) присутствует в данных с `visible: false`, но чекбокса под него в панели для казахстанского
магазина нет вообще. Вывод: **реестр столбцов таблицы шире, чем то, что реально предлагается
переключать в конкретном тенанте/локали** — колонки можно объявлять «не экспонируемыми в UI»,
просто не рендеря для них чекбокс, при этом бэкенд-схема остаётся универсальной.

## 6. Модель данных и API персистентности

Это стержень всей фичи — то, что реально нужно скопировать по духу.

### Эндпоинты
```
GET  /rest/cabinet/org/table-settings/get?tableName=PRODUCT_OVERVIEW&storeId=2690
POST /rest/cabinet/org/table-settings/save?storeId=2690
```

- `tableName` — стабильный строковый идентификатор **конкретной таблицы на конкретном экране**
  (в данном случае `PRODUCT_OVERVIEW`). У каждого списка в приложении (товары, приёмки, поставщики
  и т.д.) — свой `tableName`, все хранятся в одном общем эндпоинте/таблице настроек, не отдельными
  сущностями на каждый экран.
- `storeId` — настройки скопом на магазин (query-параметром). Сам пользователь идентифицируется
  Bearer-токеном в заголовке — то есть итоговый ключ записи, вероятно, **(пользователь, магазин,
  tableName)** (предположение: не проверено напрямую, различаются ли настройки у двух разных
  сотрудников одного магазина — по логике же org/… в пути эндпоинта не исключает, что это
  настройка на уровне организации/магазина, общая для всех сотрудников — стоит уточнить это на
  этапе дизайна, а не считать доказанным фактом).

### Тело запроса на сохранение (POST save)
Полный снэпшот на **любое** изменение (resize ИЛИ reorder ИЛИ toggle видимости — один и тот же
формат и один и тот же эндпоинт для всех трёх действий):

```json
{
  "tableName": "PRODUCT_OVERVIEW",
  "pageSize": 50,
  "columns": [
    { "columnName": "select",       "columnOrdinalNumber": 0,  "visible": true,  "sort": false, "width": 50 },
    { "columnName": "fullName",     "columnOrdinalNumber": 1,  "visible": true,  "sort": true,  "width": 200 },
    { "columnName": "barcode",      "columnOrdinalNumber": 2,  "visible": true,  "sort": false, "width": 150 },
    { "columnName": "nkt",          "columnOrdinalNumber": 3,  "visible": true,  "sort": false, "width": 150 },
    { "columnName": "vendorCode",   "columnOrdinalNumber": 4,  "visible": true,  "sort": false, "width": 100 },
    { "columnName": "aliasList",    "columnOrdinalNumber": 5,  "visible": true,  "sort": false, "width": 94 },
    { "columnName": "arrivalCost",  "columnOrdinalNumber": 6,  "visible": true,  "sort": true,  "width": 200 },
    { "columnName": "sellingPrice", "columnOrdinalNumber": 7,  "visible": true,  "sort": true,  "width": 200 },
    { "columnName": "measureValue", "columnOrdinalNumber": 8,  "visible": true,  "sort": false, "width": 87 },
    { "columnName": "markup",       "columnOrdinalNumber": 9,  "visible": true,  "sort": false, "width": 95 },
    { "columnName": "margin",       "columnOrdinalNumber": 10, "visible": true,  "sort": false, "width": 85 },
    { "columnName": "numberOnScale","columnOrdinalNumber": 11, "visible": true,  "sort": false, "width": 145 },
    { "columnName": "editTime",     "columnOrdinalNumber": 12, "visible": true,  "sort": true,  "width": 165 },
    { "columnName": "supplierName", "columnOrdinalNumber": 13, "visible": true,  "sort": false, "width": 125 },
    { "columnName": "ikpu",         "columnOrdinalNumber": 14, "visible": false, "sort": false, "width": 150 },
    { "columnName": "control",      "columnOrdinalNumber": 15, "visible": true,  "sort": false, "width": 50 }
  ]
}
```

Разбор полей на каждую колонку:

| Поле | Смысл |
|---|---|
| `columnName` | **Стабильный машинный ключ** колонки (`markup`, `sellingPrice`…), НЕ переведённая надпись. Критично для i18n и для того, чтобы переименование лейбла в UI не ломало сохранённые настройки. |
| `columnOrdinalNumber` | Позиция слева направо, 0-based, пересчитывается целиком при любом reorder. |
| `visible` | Показан/скрыт. |
| `width` | Ширина в px, целое число. |
| `sort` | Признак «эта колонка сортируемая» — это свойство самой колонки (задаётся конфигом таблицы), а не текущее направление сортировки пользователя; в ответе оно просто зеркалится обратно при сохранении. |

### Когда именно уходит запрос
Один POST на **завершение** дискретного действия:
- resize → на `mouseup`/окончание drag (не на каждый пиксель),
- reorder → на `drop`,
- toggle видимости → сразу на клик по чекбоксу (без debounce, без кнопки «Сохранить»).

`pageSize` (кол-во строк на странице) тоже часть этого же объекта — то есть у UMAG это единая
сущность «настройки таблицы для пользователя», а не три разные фичи с тремя разными местами
хранения.

## 7. Что можно унести как есть, а что — адаптировать под Shugyla

Наш стек: React 19 (без TypeScript), обычный CSS, без UI-библиотек, Supabase как бэкенд,
Adapter-паттерн (`*LocalAdapter.js` / `*SupabaseAdapter.js`, оркестратор
`src/services/platformDataService.js`).

**Прямые аналоги, которые стоит скопировать 1:1:**

1. **`table-layout: fixed` + ширина только на `<th>`.** Не нужно синхронизировать ширину `<td>`
   вручную — избавляет от целого класса багов рассинхронизации шапки и тела.
2. **Одна сущность настроек на таблицу**, а не три разные (order/width/visibility как отдельные
   штуки). Формат `{ tableId, pageSize, columns: [{ key, order, visible, width }] }` — прямой
   аналог. `key` (у нас) = `columnName` у UMAG — стабильный идентификатор, не текст лейбла.
3. **Полный снэпшот на каждое действие**, а не diff. Один метод `persistColumnsState(columns)`,
   вызываемый из трёх обработчиков (resize-end, reorder-drop, visibility-toggle).
4. **Не все колонки togglable.** Явно помечать в конфиге колонки как `lockedVisible: true`
   (аналог select/fullName/barcode/control у UMAG) и не рендерить для них чекбокс в панели
   настроек, но продолжать пересылать их в общем массиве columns.
5. **Резервировать возможность иметь в реестре больше колонок, чем показано в UI** — полезно
   для будущих ролей/тарифов (колонка есть в схеме, но `exposedInToggle: false` для части
   пользователей).

**Что адаптировать под наши ограничения (нет PrimeNG):**

- Resize-хендл: `<span>` шириной ~6px, `position: absolute; right: -3px; top: 0; bottom: 0;
  cursor: col-resize; z-index: 1;` внутри `<th>` с `position: relative`. Слушать `pointerdown`
  на хендле → `pointermove`/`pointerup` на `window` → менять `th.style.width` в реальном времени,
  на `pointerup` — вызвать сохранение.
- Reorder: либо нативный HTML5 Drag & Drop (`draggable="true"` на `<th>`, `dragstart`/`dragover`/
  `drop`), либо pointer-based drag (надёжнее в Safari/мобильных, но чуть больше кода). HTML5 DnD
  проще и достаточно для десктопной админки, как у UMAG.
- Персистентность: где хранить — по аналогии с существующими адаптерами завести
  `tableSettingsLocalAdapter.js` (localStorage, офлайн-режим) и `tableSettingsSupabaseAdapter.js`
  (таблица в Postgres вида `user_table_settings(user_id, store_id, table_name, page_size,
  columns jsonb, updated_at)`, с RLS на `user_id = auth.uid()` — нужно заранее решить, персонально
  на пользователя или на магазин/роль, в отличие от UMAG где это не выяснено однозначно).
- Минимальная ширина колонки: задать явную константу (например 50px), проверять на каждом
  `pointermove` перед применением, а не полагаться на браузерное поведение.

## 8. Открытые вопросы (не выяснены при исследовании, стоит решить на этапе дизайна)

1. Настройки таблицы у UMAG — per-пользователь или per-магазин (общие на всех сотрудников)?
   Путь эндпоинта `.../org/table-settings/...` намекает на «на организацию», но это не проверено
   заходом под двумя разными учётками.
2. Есть ли у UMAG способ сбросить настройки к дефолту (может быть скрыт где-то ещё, не в этой
   панели) — в исследованной панели такой кнопки нет.
3. Есть ли нижний предел не только для ширины, но и верхний (максимальная ширина колонки) —
   не тестировалось.
